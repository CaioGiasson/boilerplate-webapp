## Contexto

A UI deve ser integralmente traduzível. Persistência de idioma via **cookies** (`CookiesManager`), não localStorage.

## Objetivo

Configurar **next-intl** com prefixo de locale **sempre** presente e catálogos de texto sob `src/constants/texts` (ou estrutura equivalente mapeada pelo next-intl).

## Escopo

- Instalar/configurar `next-intl` no App Router.
- Rotas sempre com prefixo: `/pt`, `/en`, `/es` (ex.: `/pt/config`, `/en`, …).
- Locales: `pt` (default), `en`, `es`.
- Default quando **não** houver cookie de locale: **`pt`**.
- Arquivos de mensagens em `src/constants/texts` (ex.: `pt.ts` / `en.ts` / `es.ts` ou JSON), cobrindo no mínimo:
    - App (nome, Hello World)
    - Navegação (Home, Configurações / tooltips)
    - Settings (seção Geral, labels tema/idioma, opções do select)
- Cookie de locale lido/escrito via `CookiesManager`.
- Troca de idioma deve atualizar cookie e navegar para o mesmo path no novo prefixo.
- Middleware next-intl para resolver locale nas rotas.

## Fora de escopo

- Sidebar visual completa (mas pode exportar keys usadas pela nav).
- Tema escuro (foundation/settings).
- Tradução de erros de API backend (só UI).

## Critérios de aceite

- [ ] `/pt`, `/en`, `/es` funcionam; redirect coerente de rotas sem locale para o default/`pt`.
- [ ] Textos da UI (hello, nav, settings labels) vêm dos catalogs — zero string hardcoded de UI em componentes de página.
- [ ] Cookie de locale persiste entre reloads.
- [ ] Build ok com rotas localizadas.

## Dependências

Bloqueada por: **foundation** (`CookiesManager`). Pode seguir em paralelo com design-system após a foundation.

## Notas para o agente

Documentar chaves de mensagem usadas. Manter estrutura fácil de estender para novos menus.
